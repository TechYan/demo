SFLOW DEVELOPMENT TREE

从目录到一次
可追溯的构建

一个开发 tree 是独立的设计 Git 仓库。你在 src/ 维护 RTL、验证代码和设计元数据，在 env/ 选择平台与依赖版本，通过 run.py 执行流程，并在 out/ 查看发布、连线、编译和调试结果。

查一个目录该怎么用 ↓操作 IP / tile / config 组合图 ↓看 BIA 与地址如何接入 ↓找到结果和 rerun 命令 ↓

IP、subsystem、SoC、library 和 common 使用同一套目录骨架。构建根通过自己的平台锁选择整次构建的 runtime；被导入设计的独立平台偏好用于它自身的 standalone 开发。

交互目录与文件说明

点击路径查看归属、填写方式和消费阶段。搜索可使用路径或关键词，例如 “RTL”“feature”“rerun”。下面展示常见文件与可扩展目录，具体文件由 tree 类型和项目声明决定。

    文件放在哪里，怎样接入

    文件路径和消费声明共同决定它如何参与构建。src/ 会进入源码快照，参与编译的文件再通过 project 的 rtl 或 filesets 选择。

    你要添加的内容建议位置需要怎样声明 / 使用
    手写 RTL、package写入 project.hjson 的 rtl，或选中 fileset 的 files。package 顺序用 fileset 的 deps 表达。
    头文件与共享 include 或 RTL 相邻目录显式加入 fileset 的 include_dirs。源码所在目录参与源文件相对 include；实际 include 闭包由前端审计。
    Testbench、case、VIP用 fileset 选入 TB/VIP，config 指定 topmodule。suites 选择 plusargs、seed、timeout 和成功标志。
    项目清单与构建配置声明 name/kind、生成脚本、targets、filesets、configs、suites。config 选择 target/view/variant/feature/fileset。
    模块端口与 bundle 映射sidecar 写 module、bundle type/role 和字段到 RTL 端口的 map。project 的 interface 指向对外 sidecar。
    实例、连线、tile、顶层导出把 assembly 路径填入 targets.<name>.assembly 或相应 view。BIA 按此生成顶层与 tile RTL。
    寄存器与地址描述内置地址阶段读取根 publication 的 addresses.hjson。字段级寄存器描述及其生成器由项目配方组织。
    variant、feature 与代码生成VARIANTS 声明合法 variant 与有类型的 feature，build(context) 写入 context["output"] 并返回发布的 RTL/filesets 等信息。
    feature / fuse 的原始数据、项目可在配方中读取这些数据。当前平台的 feature 权威入口为 VARIANTS 与 config 的 features。
    公共 bundle 类型公共库按类型名提供 <type>.hjson，定义字段、master 方向与宽度；BIA 消费其发布副本。
    公共 RTL / VIP 依赖独立 sharedlib / VIP tree在 imports 中声明 Git 来源，更新锁并同步。在 fileset 的 deps 中选择需要的设计、variant 与 fileset。
    PDK、SRAM 等外部模型项目指定的绝对路径通过 fileset 的 external_files / external_include_dirs 声明。构建记录文件及实际头文件摘要。

    src/meta/assembly/ 是模板预留的项目组织目录。实际 BIA assembly 由 target/view 的 assembly 字段绑定，当前样例放在 src/meta/connectivity/。feature/fuse 目录中的项目数据也通过配方显式接入。

    两套版本声明

    平台
    env/platform.hjson + platform.lock.json 选择 sflow 代码、bootstrap API 及其锁定 Python 依赖。
    设计
    env/imports.hjson + imports.lock.json 选择设计仓库闭包，固定各仓库完整 commit。
    本地开发
    platform.local.json 覆盖平台，overrides.local.hjson 覆盖设计；实际路径和 dirty 状态进入 provenance。

    从 config 到一次执行

    target
    选择某份 assembly 或 fileset 组合。
    view
    选择该 target 下的结构 / fileset 表示，默认 tile。
    variant
    选择 VARIANTS 中已声明的生成分支。
    feature
    config 按 build unit 覆盖已声明的 bool/int/string 值，形成全局 registry 和宏。
    suite
    选择运行用例与 seed。编译配置由 config/fileset 决定。
    依赖图在哪声明决定什么
    Importenv/imports.hjson获取哪些独立设计仓库及其精确版本。
    Buildproject.build.dependencies哪个生成器先发布，供另一个生成器通过 context["dependencies"] 使用。
    Hardwareassembly 的 instances、connections哪些 design_variant 被实例化，如何连接 bundle 和划分 tile。
    Filesetfilesets.*.deps哪些源码参与当前编译、package 与其他文件的编译顺序。

    一次构建如何串联
    选择运行方式，再点击阶段查看它读什么、产生什么。SiliconCompiler 按显式依赖执行任务，同层 publication 可按依赖并行运行。
    
      
    
        
    build / 硬件构建
    
        
    具有 BIA assembly 的设计按此路径生成并编译。
    
        
    
        
    
      
    
      
    build
    生成、发布、连接、组织 filelist，并执行 Icarus compile。无 BIA 的显式 topmodule 项目沿 publication/fileset 路径组织源码。
    sim / run --build
    sim 编译一次，再按 case/seed 执行。run --build 校验指定 simulation build 的镜像摘要后，使用已有镜像运行 suite。
    lint / 公共库
    lint 使用 Slang 检查同一配置产物。没有 topmodule/BIA 的 library/common 执行 snapshot/publish，结果体现已完成的阶段。
    
    
    

    
    
      
    BIA 与寄存器地址如何接入
    两条链路都从发布后的设计输入出发。BIA 处理接口与结构连接，地址阶段由构建根分配 region。
    
      
    
        
        
      
    
      
    SoC 构建使用 SoC 根 publication 的地址分配。IP 的相对寄存器布局可保存在自身 src/meta/register/ 中，再由项目生成器按集成契约消费。

    生成地址 package 的结构
    SystemVerilog · addresses/sflow_addresses_pkg.sv
    `timescale 1ns/1ps
package sflow_addresses_pkg;
  localparam logic [31:0] DMA_BASE = 32'h00001000;
  localparam logic [32:0] DMA_SIZE = 33'h000000100;
  localparam logic [31:0] ATU_BASE = 32'h00002000;
  localparam logic [32:0] ATU_SIZE = 33'h000000100;

    根地址文件经 publish 进入 addresses 节点，package 自动进入 assembly 的编译输入。base/size 使用整数，region 需在 32 位地址空间内且互不重叠。
    
        
    项目生成配方的最小接口
    Python · build.py 接口示意，接入已有生成器时填写 emit_register_rtl
    from pathlib import Path

VARIANTS = {"default": {"DATA_WIDTH": 32}}

def build(context):
    source = Path(context["source"])
    output = Path(context["output"])
    spec = source / "src/meta/register/regs.hjson"
    generated = output / "generated/csr_regs.sv"
    generated.parent.mkdir(parents=True, exist_ok=True)
    # 在此调用项目提供的生成器，读取 spec、使用已解析 feature。
    # emit_register_rtl(spec, generated, context["features"])
    return {"rtl": ["src/rtl/core.sv", "generated/csr_regs.sv"]}
    
        
    上面的配方展示接入契约，使用前需实现生成器并准备实际文件。输出写入 context["output"]，返回的 fileset 名称与依赖结构需与已解析 project 对齐。配方可读取 context 的 feature，权威 context 由平台生成并校验。

    修复 BIA 调试副本后，重跑失败节点
    适用于已启动 SC 节点的失败。终端与结果中的 failed_nodes 会给出真实路径。以下以 bia_pcie_default/0 为例。
    
        
    1. 找到报错中的 inputs 与 command。BIA sidecar 常位于 <node>/debug/inputs/lib_pcie_default/src/meta/interface/core.hjson，assembly 位于相邻的 connectivity/。
    2. 编辑该调试副本，修复 bundle 类型、role、字段映射或连线端点。
    3. 执行保存的 rerun.sh。本地和 LSF 使用同一入口，退出码反映本次节点状态。
    4. 查看打印的 attempt 结果路径，以及其 input_changes、work_directory 和 log。
    
        
    shell · 将路径替换为失败结果给出的绝对路径
    bash /absolute/path/bia_pcie_default/0/rerun.sh

# debug 队列和资源参数按集群实际情况填写
bsub -q debug -n 1 bash \

    每次调用保存独立 attempt，原始 build 的结果继续描述首次 flow。保存的继承环境随脚本恢复，SC 在原阶段应用 overrides；当前 LSB_* 作业身份与本次临时目录由新执行提供。计算节点需能访问保存的解释器、平台、build 和外部输入路径。
    
        
    修改原始 src 后，怎样更新调试输入
    先执行正常 build/publish，取得新 build 的完整 library/<unit>/。将对应调试 publication 完整替换为新目录，保留它的 manifest/context 和文件删除结果，再执行原命令。BIA/addresses 的位置是 debug/inputs/lib_<unit>/，compile/lint 的位置是 debug/artifacts/library/<unit>/。feature/config/variant 与保存计划保持一致，改变这些选择时通过新 build 解析。

    配置选错，查看 plan.json 中的 config、variant、units、filesets 与 feature digest。

    遇到错误时
    从报错所属阶段查起，使用保存的结果路径定位具体输入。
    
      
    reference 提示先 materialize
    从平台 checkout 执行 uv run --locked sflow reference materialize --dest /tmp/sflow-guide，再进入生成的 workspaces/<design> 运行。目标目录使用新路径。
    
      
    manifest 与锁不一致，或设计来源缺失
    检查 env/imports.hjson 中的来源和 ref，执行显式 python env/sync.py update [names...] 更新锁，再同步。平台来源通过 platform update 维护。检查被引用设计是否作为直接依赖声明。
    
      
    BIA 报 unknown type / role、字段宽度或端点错误
    检查 common_info 中对应 bundle 类型、sidecar 的 type/role/map，以及 assembly 的实例名和 connections。已有失败节点时，先用 failed_nodes 的调试副本复现和修复，再用同一脚本重跑。
    
      
    新增文件未进入 filelist，或头文件搜索出现歧义
    检查当前 config/target/view 选中的 fileset 与其 files/deps/include_dirs。查看 publication 和 compile.f，优先使用可明确解析的源码相对 include 路径。外部模型和头文件通过 external 字段声明。
    
      
    Slang 提示 design element does not have a time scale
    为设计中需要一起检查的 module/package 明确一致的 timescale。当前 reference 的部分 RTL 与已带 timescale 的地址 package 混用时会触发此诊断。本页对应代码基线的完整回归中有四个已复现的相关既有失败，lint 命令会真实报告这些错误。
    
      
    仿真退出后仍失败，或卡住超时
    检查 case 的 success_marker、实际日志、错误诊断与 timeout。运行 plusargs 与 seed 写在 suite 中。成功编译的 simulation build 可用 run --build 运行其他 suite，失败节点也会保留单节点命令。
    
      
    本地通过，提交到 LSF 后找不到工具或路径
    检查计算节点能否访问保存的绝对 Python、平台、build 与外部模型路径。rerun 脚本恢复已捕获的工具和自定义环境，同时使用新作业的身份。队列和资源参数由 bsub 提供。真实 LSF 提交需在已配置集群中验证。
